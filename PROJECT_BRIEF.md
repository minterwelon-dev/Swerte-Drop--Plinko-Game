# Swerte Drop — Phaser 3 Plinko (Project Brief)

Title: **Swerte Drop**. Original, play-money sample.

## 1. Purpose

A small, maths-forward portfolio piece that shows:
- a server-authoritative instant game (client renders, a mock RGS decides),
- binomial probability and RTP tuning done properly and verified by simulation,
- a provably fair round flow with a verify screen,
- a reusable board module that can later become a **slot bonus feature** (the slot-Plinko hybrid pattern studios are shipping).

Read `AGENTS.md` first. It holds the conventions and rules. This file holds the **what** and the **order of work**.

### Goals
- Ship a classic Plinko with selectable rows and risk levels, auto-drop with limits, and a verify screen.
- Generate and verify multiplier tables so every rows x risk combination hits the target RTP.
- Build the board as a reusable module driven by bin definitions, then demo it as a slot-style **Plinko Feature** (multi-ball bonus round).
- Make it easy for a reviewer to run, read and verify (README, simulation report, demo video).

### Non-goals
- Real money, real RGS integration, real certification.
- Physics-driven outcomes. The path is decided by the server; the client only animates it.
- Copying any provider's art, names or multiplier tables.
- Social features, tournaments, bonus buy.

## 2. Game spec

### 2.1 Board
- Rows selectable: **8, 10, 12, 14, 16**.
- A board with `n` rows has `n + 1` bins.
- Each peg row sends the ball left or right with 50/50 probability.
- Landing bin = number of "right" moves (0 to `n`).

### 2.2 Risk levels
`low`, `medium`, `high`. Risk changes the **multiplier table**, not the physics or the probabilities.

| Risk | Shape | Feel |
|---|---|---|
| Low | Flat, small edge multipliers, centre about 0.5x (bins near 1x sit a few steps from the centre) | Frequent small returns |
| Medium | Moderate edges, centre below 1x | Balanced |
| High | Very large edges, centre well below 1x | Long losing streaks, rare big wins |

### 2.3 Probabilities
```
P(bin k) = C(n, k) / 2^n
```
For 8 rows the 9 bins have odds 1, 8, 28, 56, 70, 56, 28, 8, 1 out of 256. For 16 rows the two edge bins are each 1 in 65,536.

### 2.4 Multiplier tables
- 15 tables (5 row counts x 3 risks), symmetric around the centre.
- Stored as **integers in hundredths** (`MultiplierX100`, e.g. `1.50x = 150`).
- **Target RTP: 97%** for every table. Acceptance window: 96.9% to 97.1% computed analytically (`sum P(k) * m_k`).
- Generated by `scripts/tune.ts`, committed as data in `src/math/multipliers.ts`, never edited by hand.
- Design guidance (the tuner decides actual values):

| Risk | Approx. max multiplier | Approx. min multiplier |
|---|---|---|
| Low | single digits at 8 rows, low tens at 16 | about 0.5x |
| Medium | tens at 8 rows, low hundreds at 16 | about 0.3x |
| High | tens at 8 rows, up to about 1000x at 16 | about 0.2x |

Tuner approach: shape `m_k = c * exp(alpha * |k - n/2|^beta)`. Fix the centre `c` and `beta` per risk, solve `alpha` so analytical RTP equals the target, round to 2 decimals, then nudge the centre bins to correct rounding drift. If the max multiplier lands far from the guidance, adjust `beta` and re-solve.

Tuner constraints, in priority order:
1. Analytical RTP within 96.9% to 97.1% (hard).
2. Symmetric and non-decreasing away from the centre.
3. Centre (minimum) multiplier per risk: low ~0.5x, medium ~0.3x, high ~0.2x (about ±0.05).
4. Max multiplier near the guidance above (soft; the tuner reports actual maxima).

A centre near 1x is impossible at 97% RTP with a centre-minimum shape: every bin would be ≥ the centre, so RTP ≥ centre.

### 2.5 Bets and money
- Bet levels (minor units): 100, 200, 500, 1000, 2000, 5000. Multiples of 100 so `win = bet * m100 / 100` is exact integer maths.
- Starting balance: 100000 minor units (play money).
- Max win cap: 5000x bet, applied to the Stage B feature round total (`feature.ts`). Classic tables max out at 1000x, below the cap; `drop.ts` keeps a defensive clamp only.
- Display currency formatting only at render time.

### 2.6 Controls
- Bet selector, rows selector, risk selector, **Drop** button.
- **Turbo** (faster row timing) and **Skip** (jump balls to their landing).
- Up to **5 balls in flight**; each is its own round with its own nonce and result.
- **History strip**: last 20 multipliers, colour-coded by tier.
- Bin hover or tap shows multiplier and landing probability (generated from data).

### 2.7 Auto-drop
- Rounds: 10, 25, 50, 100.
- Stop conditions: single win >= X, cumulative win >= X, cumulative loss >= Y, balance below Z.
- A **loss limit is required** (pre-filled with a default, cannot be left empty).
- Auto-drop pauses when the tab is hidden and cannot start if the balance is insufficient.

### 2.8 Provably fair flow
1. Mock server generates a **server seed** (32 random bytes, hex) and shows its **SHA-256 hash** before play.
2. Player can edit the **client seed** (default random string).
3. Each drop uses `nonce` (starts at 0, +1 per drop).
4. Path bits come from `HMAC-SHA256(serverSeed, "${clientSeed}:${nonce}")`: bit `i` (byte `i >> 3`, bit `i & 7`) is the move at row `i` (0 = left, 1 = right).
5. **Rotate seed**: reveals the old server seed, commits a new hash, resets nonce.
6. **Verify screen**: enter server seed, client seed, nonce, rows, risk and it recomputes hash match, path, bin and multiplier.

Honest note to put in the README: in this mock the server seed lives in the browser, so it demonstrates the protocol, not a real trust model. Regulated markets use certified RNGs and lab testing instead.

### 2.9 Stage B: Plinko Feature (slot-style bonus)
Demonstrates the board as a bonus round for the slot.
- Trigger: a "Simulate scatter trigger" button (in the real slot this is 3 scatters).
- **Ball count wheel** awards 10 to 30 balls.
- One board (12 or 16 rows) with bins defined by `BinDef` (coin value multipliers plus **Mini, Minor, Major** jackpot bins).
- Balls drop in a rapid sequence; running total updates per landing; summary screen at the end.
- Total capped at 5000x the triggering bet.
- Public interface for later slot integration:

```ts
interface FeatureRequest { sessionId: string; bet: number; seedRef: SeedRef; }
interface FeatureResult {
  roundId: string;
  balls: { path: number[]; bin: number; multiplierX100: number; win: number; tier?: 'mini'|'minor'|'major' }[];
  totalWin: number;
  capped: boolean;
  balance: number;
}
```

## 3. Architecture summary

Full rules live in `AGENTS.md`.

```
src/math/        pure TS, zero Phaser/DOM imports; shared by MockRGS and scripts/
src/rgs/         RGS interface + MockRGS (seeds, balance, latency, errors, resume, forced outcomes in DEV)
src/state/       PlinkoStateMachine + AutoPlay controller
src/game/        Board (driven by BinDef[]), Ball, BallPool, BallPath, Bins, Hud, VerifyModal, FeatureOverlay...
scripts/         simulate.ts, tune.ts
```

Round flow:
```
Idle -> Dropping (1..5 balls in flight) -> Settling -> Idle
Idle -> AutoRunning -> Idle
Idle -> FeatureIntro -> BallCountWheel -> FeatureDropping -> FeatureSummary -> Idle
```

### Display balance vs server balance
The mock settles each drop instantly and returns the new `balance`. The client keeps a separate **display balance** that is only updated when each ball visually lands, so the UI never shows a win before the animation. When no balls are in flight, display balance must equal server balance (dev assertion).

## 4. RGS contract (mock)

```ts
interface DropRequest  { sessionId: string; bet: number; rows: 8|10|12|14|16; risk: 'low'|'medium'|'high'; }
interface DropResponse {
  roundId: string;
  nonce: number;
  serverSeedHash: string;
  clientSeed: string;
  path: number[];            // length = rows, 0 = left, 1 = right
  bin: number;               // sum(path)
  multiplierX100: number;
  win: number;               // minor units, 0..cap
  balance: number;           // after the round
}
interface SeedState { serverSeedHash: string; clientSeed: string; nonce: number; }
interface RotateResponse { revealedServerSeed: string; newServerSeedHash: string; }
```

Mock behaviours required: injectable latency, injectable failure rate, seedable test mode (deterministic server seed), resume of unfinished rounds after refresh (persisted in `localStorage`), forced outcomes in DEV only (force a bin, force edge, force a feature).

## 6. Simulation outputs

`npm run simulate -- --rows 16 --risk high --drops 10000000 --seed 42` prints:
- Analytical RTP and simulated RTP with standard error
- Hit frequency (multiplier >= 1.00x) and "win" frequency (multiplier > 0)
- Observed vs expected bin frequencies
- Mean and standard deviation of per-drop return (volatility indicator)
- Max multiplier observed, longest losing streak, 99th percentile drawdown over 1000-drop sessions
- `--all` runs all 15 tables and the feature round (including cap frequency), writes `docs/simulation-report.txt`

## 7. Acceptance criteria

- Analytical RTP is within 96.9% to 97.1% for every one of the 15 tables.
- For each table, simulated RTP over 10M drops is within 3 standard errors of the analytical value.
- Observed bin frequencies pass a chi-square test against the binomial (p > 0.001) on a fixed seed.
- Same seeds and nonce always give the same path, bin and multiplier. The verify screen reproduces any recorded drop.
- **No outcome logic in the client.** The ball always lands in the bin the response states; dev build asserts `sum(path) === bin`.
- No Phaser or DOM imports under `src/math/` or `scripts/`.
- With no balls in flight, display balance equals server balance.
- Auto-drop obeys every stop condition and cannot start without a loss limit.
- Stable 60 FPS on desktop and >= 55 FPS under 4x CPU throttle with 5 balls in flight.
- Refresh mid-drop resumes correctly.
- Production bundle contains no debug panel or forced-outcome code.
- Portrait and landscape usable, including live rotation.
